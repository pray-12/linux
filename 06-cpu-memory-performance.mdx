title: CPU, Memory & System Performance

## ⭐ Must Know

**108. How do you check CPU usage?**
`top` or `htop` for a live view, `mpstat` for per-core breakdown, or `vmstat 1` to watch CPU stats refresh every second.

**109. How do you check memory usage?**
`free -h` gives a quick human-readable summary of total, used, free, and available memory plus swap.

**110. Difference between RAM and swap.**
RAM is physical, fast memory the CPU reads/writes directly. Swap is disk space used as overflow when RAM fills up — it's much slower since it's disk I/O, so heavy swap usage is usually a performance red flag, not a solution.

**111. What is swap?**
A dedicated area on disk (a partition or swap file) that the kernel uses to move out inactive memory pages when RAM is under pressure, freeing up physical RAM for active processes.

**112. How do you check swap usage?**
`free -h` shows swap total/used, or `swapon --show` lists the configured swap devices/files and their usage.

**113. How do you check load average?**
`uptime`, or the first line of `top`, both show the three load average numbers.

**114. What is load average?**
It's a rolling average of the number of processes that are either running on the CPU or waiting for CPU/disk I/O, over the last 1, 5, and 15 minutes. It's a general measure of system demand, not strictly CPU-only.

**115. What does this mean: `load average: 1.2, 2.5, 3.1`?**
Those are the 1-, 5-, and 15-minute load averages. Load has been dropping recently (1.2 now vs 3.1 fifteen minutes ago) but was higher in the past — the trend suggests things are recovering. To know if 1.2 is "high," I need to compare it against the number of CPU cores — a load of 1.2 on a 4-core box is fine, but on a 1-core box it means things are queued up.

**116. How do you check the number of CPU cores?**
`nproc`, or `lscpu` for a fuller breakdown (sockets, cores per socket, threads per core).

**117. How do you check available memory?**
`free -h` — specifically the "available" column, which is a more realistic estimate than "free" since it accounts for reclaimable cache/buffers.

**118. How do you check system uptime?**
`uptime` — same command covered in fundamentals.

**119. What is `free -m`?**
`free` shows memory/swap usage, and `-m` displays the values in megabytes instead of the default kilobytes (`-h` for human-readable is what I usually reach for instead).

**120. What is `vmstat`?**
A tool that reports virtual memory, process, CPU, and I/O statistics — `vmstat 1` refreshes every second, which is great for watching trends like swap activity or CPU wait time in real time.

## 🔥 Scenario

**121. Server is running very slowly. What will you check?**
I'd work through it systematically: `top`/`htop` for CPU and memory hogs, `free -h` for memory/swap pressure, `df -h` for disk space, `iostat` or `vmstat` for disk I/O wait, and `uptime` for load average relative to core count. Then I'd check application/service logs for errors and, if it's network-related, `ss`/`netstat` for connection counts.

**122. Memory usage is 95%. How would you troubleshoot?**
First I'd check if that's actually a problem — Linux uses free RAM for disk cache aggressively, so I look at the "available" column in `free -h`, not just "used." If real usage is genuinely high, I'd find the top memory consumers with `ps aux --sort=-%mem`, check for a memory leak (usage climbing over time in one process), and check swap usage — heavy swapping alongside high memory means the box is genuinely under-provisioned or something's leaking.

**123. CPU is normal but application is slow. What else would you investigate?**
Disk I/O wait (`iostat -x 1`, or the `wa` column in `top`), network latency/DNS resolution delays, database query performance, thread/connection pool exhaustion, and downstream dependency latency (an API or DB the app calls). I'd also check application-level logs and GC pauses if it's a JVM-based app — plenty of "slow" issues aren't CPU-bound at all.

**124. Server load average is very high. What could be the reasons?**
Too many CPU-bound processes competing for cores, processes stuck waiting on disk I/O (high iowait), a runaway/looping process, too many concurrent requests for the app to handle, or even excessive forking (e.g. a fork bomb or misconfigured cron spawning duplicates). I'd cross-reference load average against `top`'s CPU and iowait figures to narrow down whether it's CPU-bound or I/O-bound.
