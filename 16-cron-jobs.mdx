title: Cron Jobs

**246. What is cron?**
A time-based job scheduler daemon on Linux that runs commands or scripts automatically at specified times or intervals — used for backups, log rotation, health checks, and any other recurring task.

**247. What is crontab?**
The file (and the command used to edit it) that defines a user's scheduled cron jobs. Each user can have their own crontab, and there's also a system-wide one at `/etc/crontab` plus drop-in files under `/etc/cron.d/`.

**248. How do you list cron jobs?**
```bash
crontab -l
```

**249. How do you edit cron jobs?**
```bash
crontab -e
```
Opens the current user's crontab in the default editor.

**250. Explain the cron format: `* * * * *`**
The five fields, in order, are: minute (0-59), hour (0-23), day of month (1-31), month (1-12), and day of week (0-6, Sunday=0). Each `*` means "every" value for that field, so `* * * * *` runs every single minute.

**251. How would you run a script every day at 2 AM?**
```bash
0 2 * * * /path/to/script.sh
```

**252. How would you troubleshoot a cron job that isn't running?**
First check the crontab entry itself is syntactically correct (`crontab -l`), then check cron's own logs (`/var/log/cron` or `journalctl -u cron`/`crond`) to see if it actually attempted to fire and what happened. A very common gotcha is that cron runs with a minimal environment — no `PATH`, no user profile sourced — so scripts that work fine manually fail under cron; I always use absolute paths inside the script and either set `PATH` explicitly in the crontab or at the top of the script, and redirect output to a log file (`>> /path/log.txt 2>&1`) so I can actually see errors instead of them vanishing.

**253. Where do cron logs appear?**
Typically `/var/log/cron` (RHEL/CentOS) or `/var/log/syslog` filtered for CRON (Debian/Ubuntu), or via `journalctl -u cron`/`crond` on systemd systems.
